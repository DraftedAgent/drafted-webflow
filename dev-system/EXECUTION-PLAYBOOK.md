1. Resolve exact source host and workflow ID against the approved task. Capture the published/active definition where available separately; record an explicit absence for an inactive workflow. Never serialize a truncated object or print/save plaintext JSON. 2. Store outside repository at `C:/Users/wallg/AppData/Local/Drafted/dev-system-backups/n8n/<workflow-id>/`. Verify owner-only access (plus necessary Windows admins/SYSTEM). Filename `<UTC-yyyyMMddTHHmmssfffZ>__<workflow-id>__<saved-version-id>__pre-DEV-###.clixml`; encode unsafe filename characters. Use immutable unique filenames and separate post/rollback captures. For workflow creation there is no prior definition: preserve approved creation payload encrypted and record pre-state=absent plus target account/instance; deleting the created object is a separately approved destructive rollback, not implicit cleanup.
3. Encrypt a lossless envelope containing the raw saved/published JSON strings and provenance as a Windows DPAPI SecureString exported to CLIXML. Never export a plain string/object whose nested node parameters remain plaintext. Credential references may remain inside the encrypted definition; embedded passwords/tokens, if any, are encrypted too. No credential-value retrieval is required and the snapshot does not back up the external credential store. Do not redact the restorable encrypted copy; redact only user-facing evidence.
4. Safe manifest records workflow ID/name, source instance URL, capture UTC, remote updatedAt, saved versionId, activeVersionId/active state, source Git SHA, DEV ID, encrypted-file path, SHA-256 of the exact UTF-8 raw saved and published strings and encrypted-file checksum. No node payload, header, secret, personal fixture or credential value in plaintext manifest. Protect manifest access too. Checksum enables integrity comparison; it does not replace encryption.
5. Re-import/decrypt immediately and verify both raw-string hashes and parsed definition identity; abort on any mismatch. Re-read source version/updatedAt immediately before write and abort on concurrent change. Snapshot must be complete and verified before mutation. Read-check/write race is still possible if the API lacks conditional update; no atomic concurrency guarantee is claimed.

Exact rollback: obtain approval naming workflow ID and saved-only versus published restoration; GET and encrypt the current state first; compare it with the recorded post-change version/hash and stop if unrelated intervening changes exist. Decrypt/verify the approved pre-change snapshot, derive only writable fields accepted by the instance's official update schema, preserve workflow/node IDs and referenced credentials, and PUT the prior definition to the SAME workflow ID. Do not blindly send GET-only metadata, activeVersion or active flags. GET again and compare the restored writable projection to the snapshot with canonical property ordering (array/node/connection order preserved); log expected server metadata/version changes separately. Saved restore creates a new version and does not necessarily restore the previously published version. If live state must be restored, use a separately approved supported publish/activate/version operation and credential, then GET both saved and active content and verify route/activation state. Restore original inactivity only with its own approved activation-state action when needed. Stop if the instance cannot restore the required live definition. Record hashes/provenance/outcome in DEV log. This cannot reverse model charges, email/doc writes, credential changes or other side effects.

## Default execution flow and approval points

1. Read the user request, DEVELOPMENT-CONTRACT, applicable local/site instructions, current Git state, affected contracts and current remote versions. Use inspection credentials by default. Preserve unrelated work and the Drafted-IRP-Research boundary.
2. Classify concern (UI, behavior, backend, contract, architecture, operational configuration) and change type (bug fix, implementation, contract, research-informed experiment). Identify affected files/workflow/page IDs, uncertainty and TEST-STRATEGY scenarios. Make a compact plan.
3. Proceed autonomously with requested local implementation, feature-branch setup, reversible local preparation, mocks, fixtures, local validation and documentation. Routine implementation details require no extra question. If ambiguity affects product intent or a contract, stop only dependent work; continue independent work. CONTRACT-DECISIONS is a pending queue, not approved intent.
4. Prepare isolated validation/preview. Local network must be denied or intercepted: current frontend constants point at production. Verify the test target and intercept all six routes before loading fixtures. A visual preview alone does not prove backend isolation. Mock model/renderer outputs first. No production execution as a diagnostic shortcut.
5. Staged Webflow writes and isolated n8n saved-definition edits may proceed only when the user has explicitly requested that work and the target isolation, permissions and snapshot gate are verified. Existing production workflows/site configuration are shared resources: a generic local task does not authorize their mutation. No repeated permission request is needed for actions already covered by a clear approved scope.
6. For a contract/architecture change, obtain explicit approval of the concrete proposed behavior before implementing that change. For production, finish the reviewable candidate first, then request one approval bundle naming artifact versions, exact systems/IDs, domains/route effects, deployment/publish/activation actions, order, verification, rollback and any test execution/cost. Previously granted approval remains valid within that scope; expansion requires new approval.
7. Commit/push/PR only within requested delivery scope or an explicitly adopted standing policy. Never infer remote delivery approval from inspection. Production-affecting push/merge is also a production gate. Verify automation before any remote push; if unknown, keep work local. PR creation must not automatically merge or deploy.
8. Execute only approved actions. Re-read remote versions immediately before writing; abort on concurrent change. Verify saved, active/published and served versions separately. After an uncertain mutation response, reconcile through read access before retrying. Never claim completion from an unverified deployment.
9. Append one material DEV record with before/after, touched IDs, validation and deployment status. If a material architecture decision emerged, flag "Possible design decision detected." and ask separately whether the approved choice should become DD; no formal record is automatic.

Approval is mandatory for new product intent, contract/architecture changes, production mutation/publishing/activation, production executions/retries, destructive operations, and delivery outside previously authorized scope. Inspection and explicitly requested local work are autonomous. Test-target provisioning has its own initial scope; no per-test approvals are needed once that exact isolated test plan is approved.
